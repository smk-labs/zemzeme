# D1 نقشه تحویل

حکم: **قوی**  ·  دسته‌ی وابستگی: **درون‌پروسه**  ·  پیش‌نیاز: هیچ. این واحد اول همه است. سه واحد دیگر (پنل، تنظیمات، خط لوله) اگر بعدش بیایند از این نقشه استفاده می‌کنند، ولی این یکی به هیچ‌کدام دست نمی‌زند و هیچ فایلی جز zemzeme.h و session.m و دو فایل تازه در tools/ را عوض نمی‌کند.

> این سند طرح است، نه کدِ نوشته‌شده. روی ویندوز و بی کامپایلر نوشته شد، پس
> هیچ ادعایی درباره‌ی «رفتار عوض نشد» ندارد. آن را فقط اجرا روی مک ثابت می‌کند.

## تصمیمِ گیرافتاده

تصمیمِ گیرافتاده این است: «این متن کجا برود، با امضا یا بی امضا، و بعدش سشن چه حالی بگیرد». همین حالا این تصمیم لای پنج ورودی‌خروجی نشسته: setPreviewText سر خط ۳۹۳، writeTranscript سر ۳۹۶، ZHistoryAppend سر ۴۳۷، copyFinal سر ۴۴۵ و injectAtCaret سر ۴۶۷. هیچ‌کدام از دوازده شرط بی پنل و بی کلیپ‌بورد و بی دیسک آزمودنی نیست، پس هر بار که یکی‌شان برگشت (و شش کامیت می‌گویند برگشت) فقط سر دیکته‌ی خود کاربر معلوم شد.

## آزمونِ حذف

ZPlanDelivery را بردار. پیچیدگی محو نمی‌شود، سه جا دوباره ظاهر می‌شود: deliver در session.m خط ۳۸۱، مسیر تکه‌ی دیررس در queueChanged خط ۲۳۱ که همین حالا نسخه‌ی نصفه و واگرای همان قواعد را دارد (متن خالی رد می‌شود، تاریخچه می‌نویسد، کلیپ‌بورد دست نمی‌زند)، و ZFinishResumedSession در queue.m خط ۵۰۷ که قاعده‌ی «بلندتر یا هیچ» را خودش از نو نوشته. یعنی این تصمیم از قبل سه‌جا زندگی می‌کند و آزمون حذف را رد می‌کند. برعکسش هم درست است: اگر اجراکننده را برداریم و نقشه بماند، هیچ‌چیز محو نمی‌شود و فقط پنج فراخوان لخت پشت سر هم می‌ماند، پس عمق در نقشه است نه در اجراکننده.

## رابطِ پیشنهادی

```objc
// در zemzeme.h، کنار ZChooseWritePath. خالص، بی رشته، بی حالت.
typedef NS_ENUM(NSInteger, ZDeliverAct) {
    ZActWaiting = 0,   // هیچ تکه‌ای نرسیده و همه در راه: شمار آرام
    ZActNothing,       // چیزی شنیده نشد
    ZActText,          // متن هست: بنویس و بفرست
};
typedef NS_ENUM(NSInteger, ZDeliverEnd) {
    ZEndPause = 0,     // سشن زنده، مکث
    ZEndSettle,        // تحویل شد ولی تکه در راه است
    ZEndClose,         // ببند
};

typedef struct {
    ZMode mode;
    BOOL closing;         // Esc یا دابل‌تپ
    BOOL editorTouched;   // کاربر در پنل تایپ کرده
    BOOL drained;         // صف خالی است
    NSInteger waiting;    // چند تکه در راه
    NSUInteger textLen;   // طول متن تحویل، بعد از trim
    NSUInteger caretLen;  // طول caretText بعد از trim
    NSUInteger inserted;  // چقدرش قبلا سر کرسر رفته
} ZDeliverIn;

typedef struct {
    ZDeliverAct act;
    BOOL useEditorText;   // متن مال ادیتور است، نه صف
    BOOL writeEditor;     // ادیتور تازه شود
    BOOL signClipboard;
    BOOL insert;          // درج سر کرسر
    BOOL signInsert;      // امضا روی همین درج (درج آخر)
    BOOL trailingSpace;   // یک فاصله آخر
    BOOL playSound;
    ZSound sound;
    ZDeliverEnd end;
} ZDeliverPlan;

static inline ZDeliverPlan ZPlanDelivery(ZDeliverIn in);   // ~۳۵ خط بدنه

// و درز اجرا. اجراکننده هیچ شرطی ندارد، فقط ترتیب دارد:
// پیش‌نمایش پاک، text.txt، تاریخچه، کلیپ‌بورد، درج، صدا، حال سشن.
// ترتیب جزء رابط است: تاریخچه پیش از کلیپ‌بورد و پیش از درج (کامیت 498001d)،
// و خواندن ادیتور پیش از نوشتنش (کامیت 6f24801).
```

## پشتِ درز

پشت درز پنج ورودی‌خروجی می‌ماند و هیچ‌کدام تصمیمی نمی‌گیرند: NSPasteboard از راه ZInjector copyFinal، نوشتن AX از راه injectAtCaret، history.jsonl، text.txt، و ZPanel (پیش‌نمایش، ادیتور، خط وضعیت). دو مبدل دارد، پس درز واقعی است نه فرضی: مبدل یکم خود ZSession است (خط ۳۸۱ و خط ۲۳۱ queueChanged هر دو از همین یک اجراکننده می‌گذرند)، مبدل دوم ZFinishResumedSession در queue.m خط ۵۰۷ است که پنل و کلیپ‌بورد ندارد و همان نقشه را با mode بی‌کرسر و closing بله اجرا می‌کند. تست هم مبدل سوم است، ولی به حسابش نمی‌آوریم.

### ردیف‌های جدول

1. گروگان نگیر: waiting=۲ و textLen>۰ و closing=خیر. انتظار: act=Text و end=Settle. متن همان لحظه می‌رود. از کامیت 5cabba1، یک تکه ۱٫۴ ثانیه‌ای ۱۷۴۱ نویسه را نگه داشته بود.
2. متن خالی ولی همه در راه: textLen=۰ و waiting=۱. انتظار: act=Waiting و playSound=خیر. این «چیزی نشنیدم» نیست. از 5cabba1.
3. سکوت مطلق پنل را نمی‌بندد: textLen=۰ و drained=بله و closing=خیر. انتظار: act=Nothing و end=Pause و sound=Trash. از 0cdd703، بند «سکوت مطلق پنل را می‌بست».
4. سکوت سر Esc: textLen=۰ و drained=بله و closing=بله. انتظار: act=Nothing و end=Close و sound=Trash. از 0cdd703.
5. امضای کلیپ‌بورد فقط سر خالی شدن صف: drained=خیر انتظار signClipboard=خیر، drained=بله انتظار signClipboard=بله. از 5a5242a و 5cabba1، امضا یعنی «تمام شد».
6. امضای درج مال درج آخر است: closing=بله و drained=بله انتظار signInsert=بله و trailingSpace=خیر. closing=بله و drained=خیر انتظار signInsert=خیر و trailingSpace=بله. وگرنه متن کاربر لای چند امضا تکه‌تکه می‌شود. از 5cabba1.
7. حالت کرسر و دور ادامه‌دار: mode=Cursor و closing=خیر و caretLen>inserted. انتظار insert=بله و trailingSpace=بله. فاصله دو کار می‌کند: چسبیدن تکه بعدی، و جای کرسر در متن راست‌به‌چپ.
8. دو شمارنده، نه یکی: mode=Collect و closing=خیر و caretLen>inserted. انتظار insert=خیر و writeEditor=بله. تک‌تپ در حالت جمع نشان می‌دهد، درج نمی‌کند، و Esc بعدی باید چیزی برای درج پیدا کند. از 0cdd703، بند «درج با Esc اتفاق نمی‌افتاد».
9. درج دوباره ممنوع: caretLen برابر inserted. انتظار insert=خیر و playSound وابسته به act نه به درج. این ردیف تحویل دوباره سر رسیدن تکه (queueChanged خط ۲۶۱) را می‌بندد، وگرنه یک متن دو بار سر کرسر می‌نشیند.
10. درج فقط تا اولین جای نرسیده: caretLen<textLen و waiting>۰. انتظار: insert=بله ولی طول درج از caretLen حساب می‌شود نه textLen، و signInsert=خیر. از 5cabba1 و ZQueue settledTextFrom: در سرآیند خط ۲۷۹.
11. تایپ کاربر برنده است: editorTouched=بله و mode=Collect. انتظار useEditorText=بله و writeEditor=خیر. ادیتور دست نمی‌خورد تا کاربر همان چیزی را ببیند که رفت. از 6f24801.
12. ادیتور دست‌نخورده: editorTouched=خیر و mode=Collect. انتظار useEditorText=خیر و writeEditor=بله. از 6f24801.
13. ترتیب روی سورس، تاریخچه پیش از کلیپ‌بورد و پیش از درج: grep -n در session.m باید شماره خط ZHistoryAppend را کمتر از copyFinal و آن را کمتر از injectAtCaret بدهد. از 498001d، تنها خطی که برای ماندن متن به کلیپ‌بورد و درج تکیه نمی‌کند.
14. ترتیب روی سورس، خواندن ادیتور پیش از نوشتنش: grep -n باید editorText را پیش از setEditorText بدهد، و کپی پایانی پشت صف را نگه دارد (injectAtCaret همیشه keep می‌گیرد). از 6f24801 و 6f24464، یک دیکته ۱۸۷ نویسه‌ای در sessions/2026-08-11-00-09-43 از دست رفت.

## ریسک‌ها

- ZDeliverIn هشت میدان دارد. اگر سر پیاده‌سازی به یازده رسید، یعنی داریم حالتِ سشن را کپی می‌کنیم نه تصمیم را بیرون می‌کشیم. آن‌وقت باید ورودی را برید، نه بزرگ کرد.
- نقشه رشته نمی‌گیرد و برنمی‌گرداند، پس متن‌سازی (caretText و trim و substring) در session.m می‌ماند. خطر این است که کسی وسوسه شود متن را هم به نقشه بدهد و آن‌وقت رابط هم‌اندازه پیاده‌سازی می‌شود.
- پیام وضعیت عمدا در نقشه نیست، از act و end و mode ساخته می‌شود. اگر روزی پیامی لازم شد که از این سه درنیاید، یک میدان اضافه می‌شود و همان اول شکل غلط را نشان می‌دهد.
- ZFinishResumedSession در queue.m خط ۵۰۷ قاعده‌ی «بلندتر یا هیچ» را دارد که در deliver نیست. یکی کردنشان در همین واحد، رفتار را عوض می‌کند و خط سرخ است. پس مبدل دوم فقط نقشه را مصرف می‌کند، آن قاعده سر جایش می‌ماند.
